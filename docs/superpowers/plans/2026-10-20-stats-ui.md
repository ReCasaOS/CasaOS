# Statistiques: plan du tableau de bord (CasaOS-UI)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "Statistics" system app that opens, on demand, a window showing processor, memory, network, disk and health of every container, virtual machine and the machine itself (live and 7 days), with an alert banner, per-item alert settings, a text-only dashboard notification when a resource alert fires, and a count badge of active alerts on the app icon.

**Architecture:** Three thin clients (one per service prefix) feed a pure module (`statsData.js`, like `osModules.js`) that cleans what the services send and maps contract series to apexcharts series; a second pure module formats units. A lazily loaded `StatsPage.vue` (opened by `entry.js`, like `VirtualMachines/entry.js`) merges three parallel calls into a left list with a per-service failure state, and drives one `poller.js` (one request in flight, paused when the tab is hidden). `StatsChart.vue` wraps apexcharts, one chart per contract chart id, all in one apexcharts `group` so hover is shared. Bus events `resource:alert-*` are heard by `CoreService.vue` (always mounted) and shown as text-only notifications; `alertBadge.js` (which does not import the page) reads the `alerts` counts of the list routes once and keeps a count badge on the Statistics icon in sync with the same events.

**Tech Stack:** Vue 3.5 (Options API), Buefy 3.1, vue-i18n 9 (legacy), apexcharts 4.1.0 + vue3-apexcharts 1.10.0, axios, vitest 4 + happy-dom + @vue/test-utils.

## Contract assumptions this plan relies on (check them in Task 1 and Task 11)

1. Routes exactly as contract section 2, under `/v2/app_management/stats`, `/v2/virt_management/stats`, `/v1/sys/stats`.
2. **Envelopes (contract section 2):** `/v2/app_management/stats` and `/v2/virt_management/stats` answer BARE bodies (`{items, notes}`, the Series object, `{rules, active}`; errors `{message}`), unlike those services' other routes, which wrap in `data`; the core's `/v1/sys/stats` answers `{ success, message, data }` (`model.Result`) with `data` the same body. The client unwraps by source (`data` for `core`, the body itself for the two others; Extension E1); a body of the wrong shape is a failed column, never a guess.
3. `api.get/put` in `src/service/service.js:129` prefix `/v1` unless the path starts with `/v2`..`/v9`, so the core path is written `/sys/stats` (writing `/v1/sys/stats` would send `/v1/v1/sys/stats`).
4. Series keys exactly as contract section 1 (`chart/name` or `chart/name:instance`, instance after the first `:`; instances can contain `:` and `/` for mount points). Missing key = no chart line. `null` = gap.
5. `Item.kind` drives grouping; `Item.group` (French text made by the service) is ignored. `Item.started_at` (RFC 3339 or null) and `Item.detail` (text or null) fill the header.
6. Bus properties are `map[string]string` (`CasaOS-MessageBus/model/structs.go:19`): `value` arrives as a string, parsed by the UI; the contract's unprefixed names (`item`, `name`, `kind`, `situation`, `value`, `minutes`, `since`, `source`) are read as written (existing events use prefixed names such as `vm:id`: confirm with the virt/core plans, Task 10 step 1).
8. `400 bad_rules` carries the field in `message`: `bad_rules: rules[0].threshold` (contract section 2). The page reads only the row index and the field name (`key|threshold|minutes`) from it and never displays that text.
7. A 404 from `GET /v2/virt_management/stats` or a negative `hasVirtualMachines()` means "module absent": no column and, per spec, no stats call at all. 401/5xx/timeouts mean "that column failed".

## Extensions (additions to the contract; nothing renamed)

- **E1** envelope unwrapping by source (above).
- **E2** Processor reference line (spec decision 15): `cpu/vcpus` is drawn as a horizontal line at `vcpus * 100` percent, named "Capacity of the virtual processors" for a VM and "Processor limit" for the machine; when `cpu/vcpus` is absent (containers), the note `no_cpu_limit` is absent and `scale.cpu_allocation` is a finite number above 0, the line is drawn at `cpu_allocation * 100` percent named "Processor limit"; with `no_cpu_limit` there is no line.
- **E3** The restarts and health cards are drawn only when `restarts/count` or `health/ok` exist. A VM has `health/ok` (1 running, 0 otherwise; spec decision 14), so its "restarts and health" card shows the health step line only; the machine has neither, so no card. The UI needs no change if a service adds `restarts/count` later.
- **E4** `Series.notes` codes the UI translates: `vm_memory_used_unavailable`, `no_cpu_limit`, `no_memory_limit`, `container_gone`, and for the list's own `notes` `stats_capacity`; any other code is shown as "Note from the service: {code}" (cleaned text).
- **E5** `started_at` and `detail` fill the header ("Running since {since}" for a running or paused item, the detail as one line of text cut at 200 characters). Common's unit `flag` is a fixed alias of the boolean unit.

## Review Focus (input classes the spec implies; the owning task pins each with a test)

1. A point with a missing, non-finite, negative or absurd value (`NaN`, `Infinity`, `-5`, `1e300`, a string) or a missing timestamp: drawn as a gap, never 0, never `NaN B/s` in text (Task 3, 2).
2. Hostile service text: an interface named `eth0<img src=x onerror=...>`, an item named `<b>x</b>`, a note code with markup: appears as text in list, legend, table, tooltip name and notification, never as an element (Tasks 3, 6, 8, 10, 12).
3. The selected item disappears between two polls, or the person changes item or range while an answer is in flight: the old answer never lands under the new name, the selection falls back to the first item, no endless spinner (Tasks 6, 7).
4. The tab stays hidden for an hour then shows, or the range changes quickly: one immediate ask, never a burst; no request while hidden; timers gone after close (Tasks 4, 7).
5. An item with data for one chart only (stopped container, VM without balloon, machine with no `fs`): only the charts that have data are drawn, each with its note; an all-null range says "No data for this period" and draws nothing (Tasks 3, 7, 8).
6. Alert events: unknown situation, `value: "NaN"`, invalid `since`, a flood of events, a `resolved` with no `firing` seen: bounded, text-only, deduplicated notifications (Task 10).
7. The icon badge: no call to the virt module when it is absent, no import of the Statistics page or apexcharts by the badge code, a flood of events costs at most one refresh per 2 s with one request in flight (Task 10b).
