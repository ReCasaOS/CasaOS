# Fleet (dashboard) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a master box, a "Fleet" system app shows every box of the fleet (overview, containers, VMs, updates) and runs grouped actions on them; a settings row enables the master role or joins a fleet.

**Architecture:** A `fleetApi` service wraps the core's `/v1/fleet` routes, including the relay (`/v1/fleet/boxes/{id}/relay/<path>`). A `Fleet` system app copies the Statistics pattern exactly: an `entry.js` with the card, a probe and `openFleet`, a page opened in a modal or on `#/fleet`, polled while visible. Every tab fans out one relay call per box in the browser and merges with pure functions in `fleetData.js`; grouped actions run through `bulk.js`, one request per row, one result per row. A settings modal handles the roles.

**Tech Stack:** Vue 3, Buefy 3, Vuex 4 (nothing added to the store), axios instance from `src/service/service.js`, vitest 4 with happy-dom, vue-i18n flat JSON (`en_US.json`, `fr_FR.json`).

**Spec:** `docs/superpowers/specs/2026-11-02-fleet-design.md` (in the core repository, French). The API it consumes is built by `2026-11-02-fleet-core.md` (same folder).

## Global Constraints

- Work in the worktree `D:\clients\casaos\_work\ui-fleet` (branch `feat/fleet`, cut from `inkly/main`); the checked-out `CasaOS-UI` folder is an older branch and must not be used.
- No new npm dependency.
- Strings: the English sentence is the key; every key added goes to both `src/assets/lang/en_US.json` and `fr_FR.json` (2-space indent, keep the last line without a trailing comma); reuse a key that already exists (`Virtual Machines`, `Start`, `Stop`, `Restart`, `Update`, `Close`, `Cancel`, `Open`, `Alerts`…) rather than adding a near duplicate; parameters as `{name}`.
- Anything a box answers (names, titles, messages) is rendered as text (`{{ }}`), never through `v-html`.
- Relay calls go through the axios `instance` with the explicit `/v1/fleet/...` path (the `api` wrapper would prefix `/v1` a second time); default timeout 60 s, 300 s for `GET /v1/sys/packages`, `POST /v2/app_management/image-updates`, `GET /v2/app_management/compose/updates?check=true`.
- A box that fails answers for its own row only: a 503 or network error shows that box as offline/unreachable; a 404 on `/v2/virt_management/vms` means "no VMs" and no row; the page never shows one error for every box.
- Grouped actions: one request per selected row (or per box for box-level actions), `Promise.allSettled`, a result per row: `done` (2xx), `refused` with the box's `message` (409), `offline` (503), `failed` with the status or error text (anything else).
- Commit messages: conventional (`feat(fleet): …`), **no `Co-Authored-By` trailer** (owner's rule).
- Tests: `pnpm test -- --run <path>` (vitest), each spec starting with `// @vitest-environment happy-dom`.

## Review Focus

1. A fleet of 30 boxes where one box answers each relay call in 60 s must not freeze the overview for a minute: rows render as answers arrive, the slow box shows "loading" then its result (`renders rows as each box answers` in Task 3).
2. Selecting rows, switching tab and coming back must not run a stale action on rows that disappeared from the list: `bulk` takes the rows as they are at click time, and a row whose box went offline between the click and the call shows `offline` (Task 4).
3. The enrolment code shown once must survive a copy failure: the dialog keeps it on screen until closed and shows it in a selectable field, not only behind a Copy button (Task 7).
4. A master whose own box is self-enrolled must not be offered "Update ReCasaOS" on its own row, and the Updates tab's "all boxes" selection must skip it (`self` rows excluded, Task 6).
5. A refresh that lands while a bulk action runs must not wipe the per-row results: results are keyed by `box.id + '/' + row.id` and kept across polls until the next action (Task 4).

### Task 4: Grouped actions

**Files:**
- Create: `src/components/Fleet/bulk.js`, `src/components/Fleet/bulk.spec.js`

**Interfaces:**
- Produces:
  ```js
  // Runs one relay call per row, all at once, and resolves to a Map key → { state: 'done'|'refused'|'offline'|'failed', message }
  export function runBulk(rows, call)                 // call: row => Promise (fleetApi.relay(...)); uses failureCode for the state; message is the box's `message` field or the error text
  // The calls of the spec's actions:
  export const actions = {
    app: { start: row => relay(row.boxId, 'put', `/v2/app_management/compose/${enc(row.id)}/status`, { data: JSON.stringify('start') }), stop, restart,
           update: row => relay(row.boxId, 'patch', `/v2/app_management/compose/${enc(row.id)}`) },
    vm:  { start, shutdown, reboot, 'force-off': row => relay(row.boxId, 'post', `/v2/virt_management/vms/${enc(row.id)}/force-off`) },
    box: { update: row => relay(row.id, 'post', '/v1/sys/update'),
           packages: row => relay(row.id, 'post', '/v1/sys/packages/update'),
           apps: (row, ids) => relay(row.id, 'post', '/v2/app_management/compose/updates', { data: { ids } }) },
  }
  // Polls until done, for the two box actions that have a status route:
  export function followPackages(boxId, onStatus)     // GET /v1/sys/packages/update/status every 2 s until state ∈ succeeded|failed (or offline); resolves to the last status
  export function followAppUpdates(boxId, onRun)      // GET /v2/app_management/compose/updates/run every 2 s until finished_at
  ```
  The compose status route's body is the JSON string `"start"`: axios sends a JavaScript string as it is, so the call passes `JSON.stringify('start')`, as `src/service/container.js` does for a container's status.
